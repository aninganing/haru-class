# 단계별 구현 계획

목표는 **바로 실행할 수 있는 계획**이다. 대안을 길게 나열하지 말고, 선택이 필요한 지점은 추천안과 함께 질문으로 모은다.

## 1. 파악 (병렬로)

- README.md 로드맵, CLAUDE.md, 관련 contracts·모듈·화면을 읽는다.
- 목표를 이루는 데 필요한 것을 나열한다: 데이터 모델, 엔드포인트, 화면, 비동기 작업, 외부 연동, 권한.
- `edge-cases` 스킬로 이 목표의 주요 엣지 케이스를 뽑아 둔다. 계획의 단계나 완료 조건에 반영한다.

## 2. 단계로 쪼개기

각 단계는:

- **커밋 하나 크기**이다 (`split-commit`의 묶음 하나와 대응). 리뷰 가능한 크기, 대략 파일 10개 이하.
- **혼자서도 검증된다**: 단계가 끝나면 typecheck·test가 통과하고, 가능하면 눈으로 확인할 수 있다.
- 순서 원칙: contracts → DB 스키마 → api → web → 마감 처리(엣지 케이스, 접근성, 문서).
  단, 수직 슬라이스(작은 기능 하나를 contracts~web까지 먼저 끝까지)가 위험을 더 빨리 줄이면 그쪽을 택한다.
- 외부 연동(PG, OAuth)은 가짜 구현(mock) 단계와 실제 연동 단계로 나눈다.

## 3. 병렬 그룹 표시

- 같은 그룹 안의 단계는 **서로 다른 디렉터리만 수정하고 서로의 결과를 기다리지 않으므로** 동시에 진행할 수 있다.
- 전형적인 병렬 그룹: (api 구현 ∥ web 구현) — contracts가 확정된 뒤. (테스트 보강 ∥ 스토리 보강 ∥ 문서).
- 담당을 적는다: 메인, `api-engineer`, `web-engineer`, `test-engineer`.

## 4. 출력 형식

```markdown
# <목표> 구현 계획

## 결정이 필요한 것
1. <질문> — 추천: <안> (이유 한 줄)

## 단계
| # | 단계 | 담당 | 의존 | 병렬 그룹 | 완료 조건 |
|---|------|------|------|-----------|-----------|
| 1 | contracts: 예약 스키마 | 메인 | - | - | contracts test 통과 |
| 2 | api: 좌석 홀드 | api-engineer | 1 | A | 동시 요청 테스트 통과 |
| 3 | web: 회차 선택 + 좌석 폴링 | web-engineer | 1 | A | 스토리 4상태, 테스트 통과 |
| 4 | ... |

## 단계별 메모
### 2. api: 좌석 홀드
- 바꿀 파일: ...
- 엣지 케이스: 동시 예약, 홀드 만료와 결제 승인 경합
- 위험: ...

## 검증 전략
- 단계마다 `/verify`, 마지막에 리뷰 4종 병렬 (reviewer, security-reviewer, edge-case-analyst, a11y-reviewer)
```

## 5. 저장

- 계획은 대화에 보여주고 **사용자의 수락을 기다린다**. 결정이 필요한 것은 이때 한 번에 묻는다.
- 수락 전에는 어떤 파일도 만들거나 바꾸지 않는다.
- 여러 세션에 걸칠 큰 목표면 `docs/plans/<YYYY-MM-DD>-<slug>.md`로 저장할지 함께 묻고, 수락되면 저장한다. 이후 단계가 끝날 때마다 표에 ✅를 표시한다.
