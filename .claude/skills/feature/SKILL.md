# 기능 개발 흐름

목표: 백엔드와 프론트엔드, 그리고 리뷰를 **병렬로** 진행하되, 서로 어긋나지 않게 contracts로 먼저 고정한다.
모든 단계는 **제안 → 사용자 수락 → 실행** 순서다. 메인 세션은 사용자의 수락 없이 다음 실행 단계로 넘어가지 않는다.

```
1. 계획 ─✋─> 2. contracts ─✋─┬─ api-engineer ─┬─> 4. 통합·/verify ─> 5. test-engineer ─✋─┬─ 리뷰어 4종 ─┬─> 7. 수정 ─✋─> 8. 보고 + 커밋 추천
   (메인)        (메인)         └─ web-engineer ─┘                                           └ (병렬) ──────┘
                                3. 병렬 구현 (제안 ✋ 실행)                                   6. 병렬 리뷰 (제안 ✋ 실행)
✋ = 사용자 수락 지점
```

## 에이전트 운용 규칙 (모든 단계 공통)

0. **한도**: 에이전트 한 번에 맡기는 범위는 도구 호출 약 40회·파일 15개 안(CLAUDE.md 작업 한도). 넘는 일은 묶음으로 나눠 순서대로 맡긴다. 리뷰는 기능 하나당 1라운드, 수정은 1라운드 + 재검증 1회까지. 그 뒤에도 남는 것은 사용자에게 목록으로 넘기고 다음 브랜치로 미룬다.

1. **제안 요청**: 에이전트를 `[승인]` 없이 띄운다. 병렬로 띄울 에이전트들은 한 메시지에서 동시에 띄운다. 에이전트는 읽기만 하고 제안을 돌려준다.
2. **사용자에게 전달**: 제안들을 모아 한 번에 보여준다. 에이전트별로 목표, 접근, 바꿀 파일, 확인이 필요한 것을 짧게 정리하고, 메인의 의견(충돌, 빠진 것)을 덧붙인다. 그리고 **멈추고 수락을 기다린다**.
3. **실행 지시**: 사용자가 수락하면 SendMessage로 **같은 에이전트**에 `[승인] <사용자의 수정 사항>`을 보낸다. 새 Agent를 띄우지 않는다 (제안 맥락이 이어져야 한다). 수락하지 않은 에이전트는 실행시키지 않는다.
4. 사용자가 "이번 단계는 바로 진행해" 같은 식으로 미리 수락했으면 그 단계에 한해서 2를 생략할 수 있다. 수락은 그 단계에만 적용되고 다음 단계로 이어지지 않는다.
5. 에이전트가 도는 동안 결과를 추측해서 말하지 않는다. 완료 알림을 기다린다.

## 0. 브랜치 (사용자가 실행)

- `git branch --show-current`로 확인한다. 작업 브랜치(`feat/` 등)가 아니면 아래 명령을 추천하고, 사용자가 브랜치를 만들 때까지 파일을 바꾸지 않는다.

  ```bash
  git switch develop
  git pull
  git switch -c feat/<slug>      # 성격에 따라 fix/ chore/ docs/
  ```

- 긴급 수정은 `git switch main && git pull && git switch -c hotfix/<slug>`.
- Claude는 브랜치를 만들거나 전환하지 않는다.

## 1. 계획 (메인) ✋

- `plan-steps` 스킬로 목표를 단계로 나누고 엣지 케이스(`edge-cases` 스킬)를 반영한다.
  - 엣지 케이스가 많은 도메인(예약, 결제)이면 `edge-case-analyst`에 "구현 시 대응할 것" 목록을 요청해도 된다 (운용 규칙대로 제안 → 수락 → 실행).
- 계획과 결정이 필요한 것을 **한 번에** 보여주고 수락을 받는다. 구현 중간에 같은 것을 다시 묻지 않는다.
- 단계가 여러 개면 2~7을 단계마다 반복한다. 작은 수정(파일 몇 개)은 에이전트 없이 메인에서 하되, 그 경우에도 무엇을 바꿀지 먼저 말하고 수락을 받는다.

## 2. contracts 정의 (메인) ✋

- 추가할 스키마·타입·공유 상수와 필요한 의존성을 제안하고 수락을 받는다.
- 수락 후: `packages/contracts/src/<domain>.ts` 작성 + `src/index.ts` export + 스키마 테스트, 의존성 설치(에이전트는 `pnpm add` 금지).
- `pnpm --filter @haru/contracts build && pnpm --filter @haru/contracts test`
- 날짜는 `z.iso.datetime()` 문자열. 폴링되는 응답은 필드를 최소로.

## 3. 병렬 구현 ✋

`api-engineer`, `web-engineer`를 한 메시지에서 동시에 띄워 **제안**을 받는다. 프롬프트에 넣을 것:

- 이번 단계의 목표와 범위, 1단계 엣지 케이스 중 해당 쪽 항목
- 사용할 contracts 파일·타입 이름
- 엔드포인트 목록 `METHOD /path → 응답 타입` (web은 이걸 보고 mock한다)
- 완료 조건: 에이전트 정의의 검증 명령 통과 + 보고 형식

두 제안이 서로 맞는지(엔드포인트, 필드, 에러 코드) 메인이 대조한 뒤 사용자에게 보여준다. 수락되면 두 에이전트에 `[승인]`을 동시에 보낸다.
두 에이전트는 서로 다른 디렉터리만 수정하므로 같은 작업 트리에서 병렬로 돌려도 된다. 같은 파일을 건드리는 병렬 작업만 `isolation: "worktree"`.

## 4. 통합 (메인)

- 보고의 "필요한 contracts 변경", "추가해야 할 의존성"은 사용자에게 보여주고 수락 후 처리한다.
- `/verify` 실행 (검증은 읽기·테스트라 별도 수락 없이 진행해도 된다). `pnpm dev`가 떠 있으면 `curl -s localhost:3000/api/...`로 프록시 경유 응답을 확인한다.

## 5. 테스트·스토리 보강 ✋

- `test-engineer`의 제안(공백 목록, 추가할 테스트·스토리)을 받아 사용자 수락 후 실행한다.
- test-engineer가 "발견한 버그"를 보고하면 수정 방향을 사용자에게 제안하고, 수락 후 해당 구현 쪽에서 고친다 (테스트를 버그에 맞추지 않는다).
- 변경이 작으면 5단계와 6단계의 제안을 **동시에** 받아 한 번에 수락받아도 된다.

## 6. 병렬 리뷰 ✋

리뷰어들을 한 메시지에서 동시에 띄워 **리뷰 계획**을 받고, 한 번에 수락받은 뒤 `[승인]`을 동시에 보낸다.

| 리뷰어 | 언제 |
| --- | --- |
| `reviewer` | 항상 (계약 일치, 구조, 컨벤션) |
| `security-reviewer` | 인증·인가, 결제, 프록시, 사용자 입력, 쿠키를 건드렸을 때 |
| `edge-case-analyst` | 상태·동시성·시간이 있는 로직 |
| `a11y-reviewer` | `apps/web` 화면·컴포넌트가 바뀌었을 때 |

각 프롬프트에 리뷰 범위(파일 목록 또는 "이번 단계의 변경")를 명시한다.

## 7. 수정 ✋

- 리뷰 결과를 모아 중복을 합치고 심각도 순으로 정리해 **수정 계획**으로 보여준다: 고칠 것(치명·높음·차단·심각, 돈·좌석이 틀어지는 엣지 케이스는 기본 포함 추천), 보류할 것, 각각의 방법.
- 수락된 항목만 고친다. 고칠 때 재현 테스트를 먼저 추가한다. 고친 뒤 `/verify`.

## 8. 보고 + 커밋 추천 + PR 초안

- 사용자에게: 만든 것(엔드포인트, 화면, 스토리), 검증 결과(명령별), 리뷰에서 고친 것과 남은 것, 다음 단계.
- **커밋은 하지 않는다.** `split-commit` 스킬로 커밋 묶음, 메시지, 실행 명령을 추천만 한다. 사용자가 직접 커밋한다.
- 기능의 모든 단계가 끝나면 `pr-draft` 스킬로 `.pr-drafts/<branch>.md`에 PR 초안을 쓴다 (base: develop, merge commit). 사용자가 커밋한 뒤 쓰면 커밋 목록까지 정확해지므로, 커밋 전이면 그 사실을 알리고 커밋 후 다시 갱신할 수 있다고 안내한다. push와 PR 생성은 사용자가 한다.
