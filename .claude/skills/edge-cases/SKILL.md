# 엣지 케이스

## 방법

1. 기능의 **입력, 상태, 시간, 동시 사용자, 외부 시스템**을 적는다.
2. 아래 카탈로그에서 해당하는 항목을 고르고, 이 기능에 맞는 구체적인 시나리오로 바꾼다.
3. 시나리오마다 **기대 동작**과 **대응 위치**(contracts / api / web / 둘 다)와 **테스트 방법**을 정한다.
4. 현재 코드가 이미 처리하는지 확인하고, 안 되면 "미처리"로 표시한다.

## 카탈로그

### 동시성·중복
- 마지막 1자리에 두 사람이 동시에 예약 → 한 명만 성공, 나머지 409
- 같은 사용자가 예약 버튼을 연타 / 두 탭에서 동시에 제출 → 예약 1개 (멱등키 또는 버튼 비활성화 + 서버 중복 방지)
- 같은 큐 작업이 두 번 실행 (재시도, 중복 enqueue) → 좌석이 두 번 반환되지 않음
- 호스트가 정원을 줄이는 동안 예약이 들어옴 → 정원 < 예약 인원이 되지 않음

### 시간
- 홀드 만료 직전에 결제 승인 vs 만료 작업 경합 → 둘 중 하나만 이긴다 (조건부 상태 전이)
- 회차 시작 직전·직후 예약/취소 → 시작 후 예약 불가, 취소 정책 경계 (정확히 N시간 전)
- 타임존: 서버 UTC, 화면 Asia/Seoul. 자정을 넘는 회차, 날짜만 비교하는 코드의 하루 밀림
- 클라이언트 시계가 틀린 경우 → 남은 시간 카운트다운은 서버가 준 `holdExpiresAt` 기준, 최종 판단은 서버

### 경계값·입력
- 인원 0, 음수, 최대값, 최대값+1, 소수, 문자열 → contracts 스키마에서 거부
- 빈 목록 (회차 없음, 리뷰 없음), 매우 긴 제목/설명, 이모지·특수문자
- 존재하지 않는 id, 삭제된 클래스, 이미 지난 회차의 id

### 상태 전이
- 모든 (현재 상태 × 동작) 조합을 표로: 예) CONFIRMED에서 결제 재요청, EXPIRED에서 취소, CANCELLED에서 다시 취소
- 허용되지 않는 전이는 409 + 사용자 문구. 이미 목표 상태면 멱등하게 성공으로 볼지 결정

### 네트워크·외부 시스템
- 요청 타임아웃 후 실제로는 서버에서 성공 → 재시도 시 중복 생성되지 않음
- PG 승인 성공 + 우리 DB 저장 실패 → 보상 처리(재조회, 자동 취소) 경로
- 웹훅이 늦게, 두 번, 순서가 바뀌어 도착
- Redis/DB 일시 장애 → health degraded, 사용자에게는 재시도 안내

### UI (web)
- 로딩이 긴 경우 (Skeleton), 응답이 빈 경우, API 에러, 오프라인
- 폴링 중 상태가 바뀜 (OPEN → SOLD_OUT) → 선택 중이던 회차 처리, 버튼 비활성화
- 폴링 종료: 최종 상태, 시간 초과, 탭 백그라운드, 페이지 이탈
- 뒤로 가기·새로고침으로 결제 단계 재진입, 결제 완료 페이지 직접 접근
- 좁은 화면, 큰 글꼴 설정, 다크 테마에서 레이아웃·대비

## 출력 형식

| # | 시나리오 | 기대 동작 | 대응 위치 | 현재 | 테스트 |
|---|----------|-----------|-----------|------|--------|
| 1 | 마지막 1자리 동시 예약 10건 | 1건 201, 9건 409 | api (조건부 UPDATE) | 처리됨 | e2e `Promise.all` |
| 2 | 홀드 만료와 결제 승인 동시 | 하나만 반영, 좌석 수 일치 | api | 미처리 | 단위: 두 전이 순서 바꿔 실행 |

우선순위: 돈·좌석 수가 틀어지는 것 > 사용자가 막히는 것 > 표시가 어색한 것.
